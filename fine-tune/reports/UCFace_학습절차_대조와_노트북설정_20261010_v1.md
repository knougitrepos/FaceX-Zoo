## 2. 논문과 실제 구현의 대응

| 항목 | 논문 | 현재 코드 | 판정 |
| --- | --- | --- | --- |
| 주 실험 backbone/차원 | Table I MobileFaceNet, 본문 주 실험 1024D | MobileFaceNet 1024D | 대응 |
| 사전학습 데이터 | VGGFace2 또는 MS1MV3, Table I Train Data=VGGFace2 | VGGFace2 | Table I 방향에 대응. MS1MV3 추가 불필요 |
| 후속 baseline 구성 | 사전학습 backbone에 무작위 초기화 angular-margin classifier 부착 | 새 모델/head 생성 후 backbone만 부모에서 strict load | 구조 대응 |
| 업데이트 대상 | 본문만으로 세부 freeze 정책을 확정하기 어려움 | backbone과 head 모두 optimizer에 포함 | 현재 선택을 명시해야 함 |
| 최적화 | Adam, MobileFaceNet lr=0.001, 10 epoch마다 0.1 감소, 40 epoch | 동일한 값, milestones=[10,20,30] | 40회 학습에 사용되는 LR 일정 대응 |
| baseline batch/dropout | 64 / 0.6 | 64 / 0.6 | 수치 대응. dropout 삽입 위치는 별도 구현 선택 |
| 저해상도 ArcFace | m=0.6, s=64 | 동일 | 대응 |
| 저해상도 AdaFace | m=0.4, s=64, h=0.333 | 동일, t_alpha=0.01 추가 | 본문 값 대응. t_alpha는 공식 구현 참고 선택 |
| MagFace | (la,ua,lm,um,lambda_g)=(10,110,0.45,0.8,20) | 동일, scale=64 | 다섯 값 대응. scale=64를 본문 직접 명시라고 쓴 주석은 부정확 |
| 부모 학습 loss·공유 방식 | Table I의 미조정 ArcFace 행과 사전학습 설명 존재 | ArcFace 부모를 세 head가 공유 | 가능한 설계이나 저자의 정확한 절차라고 확정 불가 |
| 두 단계의 데이터·일정 | 본문에 단계별 전체 recipe가 제시되어 있지 않음 | 같은 VGGFace2 95% 목록으로 40+40 epoch | 프로젝트 선택. 두 단계별 40회까지 직접 명시됐다고 단정 불가 |
| 분할 | 95:5 분할 명시 확인 못함 | 원본 목록의 매 20번째 행을 validation으로 분리 | 이미지 단위 자체 분할, identity-disjoint 평가 아님 |
| 전처리·증강 | 본문에서 현재의 구체적 범위/순서를 확인 못함 | BGR, 단순 resize, 고정 정규화, flip/회전/scale | 구현 선택. 얼굴 정렬 및 저자 구현 동일성 미검증 |
| 반복 | Table I 평균 5회 | seed_list 선언, 노트북 실행은 seed 하나 | 5회 자동 실행 아님 |
| 고화질 표 | Table III ResNet-50, 원 논문의 head 설정, single run | MobileFaceNet + 저해상도 head 설정 유지 | 동일 표 재현 아님. 고정 모델 교차 데이터셋 평가로 해석 |

현재 노트북 흐름은 다음과 같다.

```text
VGGFace2 Flag=1 identity -> 같은 identity들의 이미지 목록 95:5 분할
  -> 02: 무작위 MobileFaceNet + ArcFace, train 95%로 40 epoch
  -> 완료 부모 backbone
  -> 03: 새 ArcFace / AdaFace / MagFace head, 부모 backbone 로드
  -> 같은 train 95%로 backbone과 head 모두 40 epoch 추가 학습
  -> 04: 학습 head 제거, backbone export
  -> 이후 ronbun에서 frozen inference / Origin·PQ / Continuous FIQA
```

부모에 학습된 head를 그대로 잇는 단순 resume와 03의 새 classifier fine-tuning은 구분된다. ArcFace 분기 역시 새 head를 만든다. 이를 구현한 논리에 즉시 모순은 없지만, UCFace의 실제 baseline 생성 recipe와 완전히 같다는 증거는 부족하다. 반대로 본문만 보고 SurvFace/TinyFace fine-tuning을 필수로 추가할 근거도 없다.

현재 목표는 UCFace 추가 loss를 제외한 baseline 생성이므로 projection head, LU, contrastive batch 128을 추가할 필요는 없다. UCFace 방법 자체를 재현한 모델이라는 표현은 사용하지 않는다.

## 3. 확인된 설정·안내 문제

### A. YAML의 전처리 변수와 실제 입력이 분리되어 있음

`dataset.input_size`, `pixel_mean`, `pixel_std`를 수정해도 두 학습 노트북은 이를 `build_dataloader`에 전달하지 않는다. `FaceImageDataset`은 기본 112x112와 코드에 고정된 `(x-127.5)/128`을 사용한다. 현재 기본값에서는 수치가 일치하지만 사용자 설정 가능 변수로 오해하면 안 된다.

짧은 재현: YAML 상당 설정을 96x96, mean=0, std=1로 바꾸고 노트북과 동일한 loader 호출을 실행했다. 실제 출력은 `[1,3,112,112]`, 흰 이미지 최대값 0.99609375였다. 실험 조건 변경이 적용되지 않음을 확인했다.

`dataset.image_root`와 `processed_root`도 현재 두 학습 노트북의 입력 선택에 사용되지 않는다. 실제 입력은 `raw_root`와 train/val list다. `01`의 목록 출력은 `FINETUNE_DIR/data`로 고정돼 있어 YAML list 경로만 바꾸면 준비·학습 경로가 어긋날 수 있다.

### B. KEEP_RAW_RESULTS의 노트북 변수 수정은 학습기에 연결되지 않음

노트북은 YAML에서 읽은 값을 표시하지만 `Trainer`는 `common_cfg['project']['keep_raw_results']`를 다시 읽는다. 노트북의 별도 변수만 False로 바꾸면 Trainer는 True일 수 있다. 별도 재현에서 확인했다.

현재 실제 조정 위치는 `common.yaml`의 `project.keep_raw_results`다. False이면 이전 중간 periodic checkpoint를 정리한다. 원본 이미지나 부모 checkpoint 삭제 옵션이 아니다. 노트북 지역 변수와 설정을 동기화하는 수정이 필요하다.

### C. 00의 완료 출력이 검증 결과에 종속되지 않음

`00`은 파일 존재·크기·일부 표본 확인 후 마지막 셀에서 archives intact, preprocessing validated 등을 상수로 출력한다. branch assert도 try/except에서 잡아 계속 진행한다. 표본 파일이 없으면 이미지 검사가 실행되지 않아도 마지막 출력은 같다. 이 문구는 전체 압축 무결성·전체 이미지 준비 완료 증거가 아니다.

### D. 반복과 재실행

`seed_list`는 실제 반복 루프에 연결되지 않는다. 기본 seed=8972 한 번만 실행된다. Table I의 5회 조건을 따르려면 선언된 seed별로 부모와 세 분기 학습·export를 실행하고 완료 수를 집계해야 한다. `PARENT_SEED` 기본값이 현재 seed를 따르므로 다음 seed에서는 그 seed의 부모가 필요하다.

## 4. 사용자가 조절할 변수와 주의점

| 위치/변수 | 주의점 |
| --- | --- |
| 02의 STAGE/HEAD | pretrain/arcface 유지. HEAD 문자열을 바꿔도 셀 3의 실제 ArcFace 생성은 바뀌지 않음 |
| 03의 HEAD | arcface/adaface/magface를 하나씩 선택. 세 head가 같은 부모·분할을 사용하도록 유지 |
| 04의 HEAD | 방금 완료한 03의 head와 일치시킬 것 |
| project.seed / PARENT_SEED | 기본 8972. 한 반복 내 세 head는 같은 seed·부모 정책을 유지. seed_list만 수정해 자동 실행된다고 생각하지 말 것 |
| RUN_SMOKE_TEST | True는 더미 forward/backward 확인이며 정식 모델 생성이 아님. 해당 smoke 분기는 optimizer.step을 수행하지 않음. False는 셀 실행 즉시 장기 학습 가능 |
| RESUME_CKPT | 처음은 None. 중단 재개만 같은 stage/head/seed/설정/부모의 checkpoint 지정. 부모 로딩과 resume를 혼동하지 말 것 |
| PARENT_CKPT_PATH / PARENT_HASH_PATH | 대응하는 완료 부모와 그 hash JSON 사용. 세 분기에서 동일 부모 hash를 확인 |
| common.yaml의 keep_raw_results | 현재 실제 보존 제어 위치. 노트북 변수만 변경하지 말 것 |
| num_workers | 처리량 조정용. 변경값 기록. bitwise 동일성까지 검증됐다고 간주하지 말 것 |
| batch_size | 64 유지. VRAM 때문에 줄이면 논문과 다른 조건이며 AdaFace EMA/BatchNorm에도 영향 |
| epoches / TARGET_EPOCH | 40 유지. 부모 검증과 export에도 40이 별도로 고정돼 있음 |
| feat_dim / out_h / out_w | 1024 / 7 / 7 유지. 04는 1024D·112 입력 경로가 고정돼 있음 |
| optimizer/lr/milestones/dropout/head 파라미터 | 논문 대응 조건이므로 임의 조정 금지. 바꾸면 별도 실험으로 기록 |
| raw_root/train_list/val_list | 실제 데이터와 목록이 대응해야 함. 학습 중 01을 다시 실행해 공유 목록을 덮어쓰지 말 것 |
| input_size/pixel_mean/pixel_std/image_root/processed_root | 현재 표시 설정과 실제 연결이 다르므로 YAML만 수정해서 실험 조건을 바꾸지 말 것 |
| paths.checkpoint_dir/export_dir | F 드라이브 등 용량 있는 곳. 같은 stage/head/seed 이름이 재사용되므로 다른 실험 설정은 별도 출력 root 사용 |

입력/정규화·학습 조건을 바꾸기보다 현재 명시 설정을 고정하고, 경로·head·실행 모드·재개 checkpoint를 우선 조정한다. Python 모듈 변경 후 또는 head/seed를 바꿔 별도 run을 실행할 때는 커널 재시작 후 순차 실행한다.

권장 연구 표현: “UCFace Table I에 명시된 backbone·차원·최적화·head 조건을 참고하여 VGGFace2 기반 baseline을 구성하고, 미명시 세부 조건을 별도로 기록하였다.”

사용자의 ‘정확히 동일’ 기준으로는 아직 승인할 수 없다. 추가 코드 테스트만으로 논문에 없는 recipe를 확정할 수 없으며, 저자에게 재질문하는 것을 진행 조건으로 삼지도 않는다. 확보한 근거와 구현 선택을 구분한 뒤, 고정 checkpoint 내 FIQA 적용 전후를 같은 cohort와 평가 조건에서 비교하는 것이 현재 코드가 뒷받침하는 범위다.
